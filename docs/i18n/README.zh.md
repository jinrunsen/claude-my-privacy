# 维护双语文档

[English](README.md) | 中文

按照以下审查与检查流程，以英文和简体中文维护 MyPrivacy 文档。任一语言均可作为更新的原文。两侧文件必须传达相同的行为、条件、限制和示例。

<a id="scope-and-file-names"></a>

## 范围与文件名

项目自有的 Markdown 文档以同目录文件配对：英文 `foo.md`、中文 `foo.zh.md`，以及一致性记录 `foo.i18n.yaml`。范围包括 README 文件、用户和开发者指南、验证说明和 `AGENTS.md` 指令。

根目录 `.agents/` 和 `.agent/` 中的本地 agent（智能体）材料不纳入配对。[术语表](terminology.md) 在单个文件中提供双语内容，也不需要对侧文件。许可文本、代码、fixture（测试前置数据）、生成产物和历史 JSON 证据不属于翻译目标。检查器会自动发现其他项目 Markdown 文件，包括未跟踪文件。

每篇英文页面在 H1 标题后紧接 `English | [中文](foo.zh.md)`，链接到中文对侧文件。中文页面使用 `[English](foo.md) | 中文`。每种语言各保留一份说明，不要将两篇完整文档放在同一个文件中。

<a id="translation-and-review"></a>

## 翻译与审查

翻译前先阅读[术语表](terminology.md)，再按以下步骤审查每处修改的段落：

1. 阅读完整的原文段落，并用目标语言自然重述。
2. 保留每个执行主体、动作、条件、例外、数量限制和确定程度。不添加行为，不遗漏限制。
3. 保持标题层级、列表类型和编号、表格结构和行序、强调格式以及物理行数一致。每个段落占一个物理行。
4. 围栏代码块、其语言标注和注释，以及行内代码必须逐字节一致。保留外部 URL 和非文档路径。
5. 配对文档的链接在英文侧使用 `.md`，中文侧使用 `.zh.md`。保留相同的查询参数和片段。在两侧文件的每个 H2 和 H3 前放置相同的显式锚点，使用原文标题的 GitHub slug，并在锚点前后留空行。
6. 单独阅读译文，检查表述是否自然，再逐条对照两侧语义。完成审查后才能记录配对。

已有配对只翻译发生变化的段落，保留未受影响且已审查的措辞。重命名或删除时，应同时处理三个同目录文件。未确定的术语保持英文，直到术语表记录了确定的译法；在报告中将其列为待定术语，不得擅自创造译法。

<a id="check-and-record-a-pair"></a>

## 检查并记录配对

在仓库根目录运行以下命令。只需 Python 3.9 或更高版本，检查器仅使用标准库。

```sh
python3 scripts/check-translations.py --list
python3 scripts/check-translations.py README.md
python3 scripts/check-translations.py --write README.md
python3 scripts/check-translations.py
```

常规检查会拒绝缺少对侧文件或记录、哈希陈旧、结构不匹配、本地链接失效、链接语言不正确、语言切换行格式错误和空白错误的配对。`--list` 显示每个配对的状态，不修改文件。`--write` 必须显式指定配对路径；只有审查了所有配对后，才能使用 `--write --all`。写入记录前，结构和链接检查必须通过。

记录以同目录文件名为键，保存两侧文件与 Git 兼容的 SHA-1 blob hash。哈希根据文件字节在本地计算；记录操作不会暂存、提交、创建 Git 引用或上传文件。后续更新使用普通文件差异和版本控制。

门禁检查结构，以及当前字节是否与上次确认时一致。它无法判断翻译是否忠实、自然或符合事实。通过门禁是对双语审查的补充，不能代替双语审查。

<a id="maintaining-the-checker"></a>

## 维护检查器

检查器由 [check-translations.py](../../scripts/check-translations.py) 实现。其测试覆盖有效配对和刻意构造的失败情况，包括缺失文件、陈旧记录、代码变更、语言错误的链接和部分删除。

```sh
python3 -m unittest discover -s scripts/tests -p 'test_*.py'
```

修改文档无需重新运行插件执行测试，除非文档描述的运行时行为也发生变化。私有配置应保留在仓库之外，两种语言均只使用虚构示例。
